## 4. 对抗性发现（F1–F5，含裁定）

### F1：链式关闭时是否仍有旁路把参考帧泄漏给适配器？
**裁定：无旁路。** 穷举两处调用方：

| 调用方 | 位置 | 是否受门禁 |
| --- | --- | --- |
| `DirectorAgent.run()` | `director_agent.py:80` | ✅ `chain = self.chain_enabled(config)`（:71），`chain` 为假时 `previous_frame` **恒 `None`**，且不进 `_ensure_scene_anchor` |
| `TaskManager.retry_shot()` | `task_manager.py:696`（`generate_single`）/ `:692`（`_rebuild_previous_frame`） | ✅ 本轮补上 `if director.chain_enabled(config)`（:693）——**这是修复前唯一真实旁路**：重试会绕过总开关把参考帧硬塞给不支持 i2v 的提供方 |

`_rebuild_previous_frame` 仅被 `retry_shot` 调用（`:692`），无其它引用。

### F2：`_coerce_bool("2")` → `None` → `anchor_image` 被强制 `False`，是否「静默改变用户意图」？
**裁定：可接受，且方向刻意不对称 —— 这是成本安全，不是静默篡改。** 理由：

1. **不静默**：会写 warning「检测到无法解析的 anchor_image=…，已按缺省处理」，可在日志自查；
2. **代价不对称**：误开 = 花钱；误关 = 只是少一个可选优化。因此**只有付费开关**在无法解析时强制 `False`；
   `consistency_lock` / `chain_continuity` 无法解析时是**删键走默认 `True`**（零成本项，宁可用上）。
   ⚠️ 后人若看到这个不对称，**不要当成 bug 去"修平"**；
3. 能正确表达的写法很多（`true/1/"yes"/"on"`），写 `"2"` 属于越界输入。

### F3：`_ensure_scene_anchor` 是否仍在吞 `AttributeError`？
**裁定：不再吞。给出源码级证据。** 探测在 `try` **之前**：

```
director_agent.py:217  def _ensure_scene_anchor(...)
                 :246      if not getattr(config, "anchor_image", True): return None
                 :249      generate_image = getattr(self.video, "generate_image", None)
                 :250      if not callable(generate_image): return None      # ← 能力探测，静默降级
                 :253-255  ...  frames_dir / anchor_jpg ...
                 :256      try:                                          # ← try 仅从"生成段"开始
```

能力判定全部走 `getattr`（缺方法 → `False`/`None`，不抛异常）；`try/except` 现在**只**包住真正的
生成调用，用于「真实接口失败 → 回退文生视频、不中断流水线」。另见 `_supports_first_frame()`（:201）同样以 `getattr` 做探测。

### F4：`retry_shot` 每次重试多打一条 warn，是否可接受？
**裁定：可接受，不修。** 实测「连续重试 3 次 = 3 条 warn」。理由：重试是**用户单次主动操作**
（不是批量循环），每条 warn 恰好对应一次「本次重试将不带参考帧」的事实，属于**有用信息**而非噪声。
真正要消除的是**逐镜刷屏**（N 镜 N 条），已由 A2 证明解决。

### F5：两层 `supports_first_frame` 是否语义冲突 / 掩盖故障？
**裁定：语义一致（都是"不可用即 False"），但存在一层**防御性冗余**。**
`VideoGenerator.supports_first_frame()` 内部 `except Exception → return False`（静默），
因此导演层 `_supports_first_frame()` 的「探测失败」分支在生产路径上**不会触发**（实测 warn 条数 = 0）。
- **不是缺陷**：两层都朝"安全侧"（关闭链式）收敛，不会误开；
- **风险**：适配器侧的静默 `except` 会**吞掉真实故障**（如适配器内部 bug），使问题只表现为"链式莫名关闭"；
- **处置**：已用 `tests/test_consistency_adversarial.py::TestDoubleLayerCapabilityFallback` **钉住现状**
  ——若哪天适配器不再静默兜底，该用例会失败并提示重新评估。

## 6. 边界与遗留

1. **独立复核缺失**（见 §1）——限流重置后建议补一次；
2. **`anchor_image` 默认开启且会真实计费**：用户当前配置指向 H3 端点，`anchor_image` 未显式写
   → 走默认 `True` → 每个新场景会调用一次 RunningHub 文生图。**若不想付费，请显式设为 `false`**
   （已在 `docs/使用说明.md` Q17 说明）；
3. **F4** 的重试 warn（每条 1 次）为有意保留；
4. **F5** 适配器层静默 `except` 会掩盖真实故障，目前以测试钉住、未改动（改它属于另一增量）；
5. **「锁脸」能力上限**：本方案的一致性来自「提示词锁定卡 + 上一镜末帧作首帧」，属**工程近似**，
   并非身份级锁定（无 seed、无角色参考图通道）。若需真正的角色一致性，需要参考图能力模型，
   见交付说明中的部署评估。
