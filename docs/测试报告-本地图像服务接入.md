## 3. 对抗性发现（G1–G5 + 附加 G6）

### G1：`ensure_image_engine` start 成功后**未二次探活**即返回 `switched=True`
**裁定：可接受（建议后续加固，非阻塞缺陷）。**

- **证据**：实测 `health` 仅在 start 前调用 **1 次**（`sw._image.health.call_count == 1`），start 返回 0 后直接 `return {"switched": True, ...}`（`engine_switch.py:103-113`）。
- **为什么不判 bug**：
  1. 契约上 `start.sh` 本身**阻塞到 `/health` ready:true 才返回**（`deploy/image_server/README.md` §4「start.sh 会等待 /health 的 ready:true」），故 returncode 0 语义上已隐含「就绪」；
  2. 即便 start.sh 不守契约（返回 0 却未就绪），紧接着的 `generate()` 会**快速失败**（连接拒绝/非 ready），导演层 L1→L4 阶梯**逐级吞错**，不会卡死、不会付费回退。
- **建议加固**（可选）：start 成功后追加一次 ≤3s `GET /health` 探活，未 ready 则置 `degraded=True`，把「start 脚本不守契约」也纳入降级而非依赖下游兜底。

### G2：`image_runninghub_adapter` 与 `image_local_adapter` 的空端点默认语义是否一致
**裁定：一致且正确，无「选了 runninghub 却仍连 8090」的交叉接线。**

- **证据**：
  - `ImageAdapterLocal(Config(image_endpoint="")).endpoint` → `http://127.0.0.1:8090/v1/images/generations`；
  - `ImageAdapterRunningHub(Config(image_endpoint="")).endpoint` → `/openapi/v2/rhart-image-n-pro-official/text-to-image`，`base_url` → `https://www.runninghub.cn`（**无 8090**）。
- 两 provider 各自落回自家默认，`image_endpoint` 仅作「显式覆盖」，交叉接线风险为 0（`image_runninghub_adapter.py:38-47`）。

### G3：`ShotResult` 新增 `first_frame_path` 是否破坏前端/序列化/既有断言
**裁定：未破坏，安全。**

- **证据**：
  1. 全量 grep `tests/` 中**不存在**任何对 `ShotResult` 字段集的 `set(...)`/`fields_set`/`keys()` 断言（既有 `set(body.keys())` 只针对 RunningHub 请求体）；e2e_smoke 只断言 `shots[].state` / `shots[].prompt`；
  2. 实测 `ShotResult(...).model_dump(mode="json")` 序列化含 `first_frame_path=None`，旧字段（`video_path`/`frame_path`/`state`）逐字保留；
  3. 字段带 `= None` 默认、仅增不改，Pydantic `extra="ignore"` 前端多余字段亦容忍。

### G4：`chain_continuity` 语义「只门禁 L3」——文档/测试/代码是否三方一致
**裁定：代码与测试一致，但 `docs/使用说明.md` 与 `director_agent.py` 模块 docstring 存在**文档滞后**（需修文档，非功能性 bug）。**

- **代码**（`director_agent.py:405-422`）：L2 锚图门禁 = `anchor_image`（`_ensure_first_frame` L2 段），L3 门禁 = `chain_continuity`（L3 段）——即 chain 只门禁 L3。
- **测试**（`test_consistency_increment.py:425` `test_chain_continuity_disabled_disables_previous_frame_only`）：断言「关 chain → 只断 L3，L2 锚图仍生成」——与代码一致（该用例在 435 中 PASS）。
- **文档**（`docs/使用说明.md` §3.5，行 188）仍写「想彻底断链 → 关 chain_continuity：程序**源头断链，既不出开场帧，也不再传末帧**」——其中「既不出开场帧」与现行代码**矛盾**（关 chain 后 `anchor_image=True` 仍会生成锚图）。
- **源码 docstring**（`director_agent.py:4-8`）仍描述旧语义「chain_continuity 为真 → 进入新场景先以场景开场帧为链首」，与现行「锚图由 `anchor_image` 门禁」不一致。
- **补充（PRD 层面）**：`增量PRD` §5 裁定 5 写「anchor_image 走 **video_provider** 文生图」「仅 `shot_first_frame=false` 时生效」，而设计 §1.4/代码已定稿为「L2 锚图经 **ImageGenerator**」「L1 失败也降级到 L2」。设计文档已在 §1.4「关键口径」与 §9 记录该口径修正，属**已裁定**，但 PRD 文件正文未回改。
- **处置**：同步 `docs/使用说明.md` §3.5（chain 只门禁 L3）、更新 `director_agent.py` 模块 docstring；PRD 文件是否回改由 PM 定夺。**均不涉及行为代码。**

### G5：`ip_scale` 的 Pydantic `ge=0.0, le=0.6` 与 `_sanitize` 钳制是否双重生效 / 会否整份重置
**裁定：双重生效、各司其职，无「整份重置」风险。**

- **证据**：
  1. 直接构造 `Config(ip_scale=9.0)` → 抛 **`ValidationError`**（Pydantic `ge/le` 生效，用于 API 入参/直接构造）；
  2. 磁盘加载路径：`_sanitize_extended_fields` 在 `Config.model_validate` **之前**先删键（`ip_scale=9.0` → warn「已按缺省处理」→ 删键 → 走默认 0.4），实测 `llm_model="keep-me"`、`shot_count=5` **逐字保留**，未触发旧 `_migrate` 的「整份重置」教训。
- 两层不是冗余：`_sanitize` 护「磁盘脏值不炸整份配置」，Pydantic 约束护「直接构造/API 不静默接受越界」。

### G6（附加发现）：L3「上一镜末帧」**跨场景不重置**——边界观察
**裁定：低危边界观察（建议知晓，非阻塞）。**

- **证据**（实测）：`image` 全失败 + `chain_continuity=True`、3 镜 2 场景时，第 3 镜（scene1 首镜）回落 `frames/frame_002.jpg`（scene0 的末帧）作首帧，**跨场景承接**，与文档「同一场景内链式 / 换场景重置」不符：
  ```
  shot2(scene1 首镜): first_frame_path='frames/frame_002.jpg'   # 来自 scene0
  ```
- **根因**：`run()` 的 `previous_frame` 传播（`director_agent.py:97-98`）**无场景边界判断**；旧行为里场景首镜总被 L2 锚图「掩盖」，故该跨场景承接此前不显式出现。Phase 2 默认路径（L1 主路径）下，仅当「L1 失败 **且** L2 锚图也失败/关闭」时才会显形。
- **影响**：仅画面衔接不佳（新场景首帧用了上一场景末帧），**不崩、不花钱、不丢片**。若需严格「同场景」语义，可在 L3 段加 `_is_scene_head` 判断或按场景重置 `previous_frame`。本报告列为「遗留」，是否修由 team-lead 决定。
